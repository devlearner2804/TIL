# Toolnet.Be 배포 매뉴얼 56~60

## 56~60. 브랜치 작업 규칙

### 56. 작업 전 develop 최신화 필수

브랜치를 새로 만들기 전에는 반드시 `develop` 브랜치의 최신 변경사항을 받아와야 한다.

```bash
git checkout develop
git pull origin develop
```

이 과정을 생략하면 다른 팀원의 최신 코드가 빠진 상태에서 작업하게 되어 충돌이나 배포 오류가 생길 수 있다.

### 57. 변경사항이 있는지 확인

브랜치를 바꾸거나 pull을 받기 전에 현재 작업 중인 변경사항이 있는지 확인한다.

```bash
git status
```

변경사항이 없다면 다음처럼 보인다.

```text
working tree clean
```

변경사항이 있다면 먼저 commit하거나 stash해야 한다.

```bash
git add .
git commit -m "작업 내용"
```

또는 임시 저장한다.

```bash
git stash
```

### 58. 기능 브랜치 생성

`develop`을 최신화한 뒤 기능 브랜치를 만든다.

```bash
git checkout develop
git pull origin develop
git checkout -b feature/backend-deploy-manual
```

브랜치 이름은 팀 규칙에 맞춘다.

예시:

```text
feature/login-api
feature/docker-compose-update
fix/sqlite-db-mount
hotfix/backend-restart-error
docs/backend-deploy-manual
```

### 59. 작업 중에도 develop 변경사항 확인

작업 시간이 길어지면 중간에 `develop` 변경사항이 생길 수 있다.

이때는 다음 순서로 최신 변경사항을 반영한다.

```bash
git checkout develop
git pull origin develop
git checkout feature/backend-deploy-manual
git merge develop
```

또는 팀에서 rebase를 사용한다면 다음처럼 한다.

```bash
git checkout feature/backend-deploy-manual
git fetch origin
git rebase origin/develop
```

merge와 rebase 중 무엇을 사용할지는 팀 규칙을 따른다.

### 60. 브랜치 작업 시 반드시 적어둘 것

브랜치 작업 중 다음 내용을 PR이나 작업 기록에 적는다.

```text
1. develop 최신 pull을 언제 받았는지
2. 작업 브랜치 이름
3. 변경한 파일 목록
4. Dockerfile 변경 여부
5. docker-compose.yml 변경 여부
6. .env 변경 필요 여부
7. DB 삭제 또는 마이그레이션 필요 여부
8. 배포 후 확인한 명령어
```
