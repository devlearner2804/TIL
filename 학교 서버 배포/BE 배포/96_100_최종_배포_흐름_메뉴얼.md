# Toolnet.Be 배포 매뉴얼 96~100

## 96~100. 최종 배포 흐름

### 96. 로컬 작업 시작 흐름

작업 시작 전 `develop` 최신화를 반드시 한다.

```bash
git checkout develop
git pull origin develop
git checkout -b feature/backend-work
```

작업 중 변경사항을 확인한다.

```bash
git status
git diff
```

### 97. 로컬 작업 완료 흐름

작업 완료 후 변경사항을 커밋한다.

```bash
git status
git add .
git commit -m "docs: 백엔드 배포 매뉴얼 추가"
```

원격 브랜치로 push한다.

```bash
git push -u origin feature/backend-work
```

GitHub에서 PR을 만든다.

```text
base: develop
compare: feature/backend-work
```

### 98. PR 작성 시 포함할 내용

PR에는 다음 내용을 적는다.

```text
1. 작업 내용
2. 변경 파일
3. 테스트 여부
4. 배포 영향도
5. .env 변경 필요 여부
6. Docker 재빌드 필요 여부
7. DB 삭제 필요 여부
8. develop 최신 pull 반영 여부
```

예시:

```text
develop 최신 pull 반영 완료
Dockerfile 변경 없음
docker-compose.yml 변경 있음
.env 변경 필요 없음
DB 삭제 필요 있음
배포 후 sudo docker ps, backend logs 확인 필요
```

### 99. 서버 배포 전체 명령어

서버에서 직접 배포할 때 전체 흐름은 다음과 같다.

```bash
cd /path/to/toolnet-be
git checkout develop
git pull origin develop
sudo docker-compose down
sudo docker-compose up -d --build
sudo docker ps
sudo docker-compose logs --tail=100 backend
```

DB 삭제가 필요한 배포라면 다음 순서로 한다.

```bash
cd /path/to/toolnet-be
git checkout develop
git pull origin develop
sudo docker-compose down
sudo rm -rf Grape.db
touch Grape.db
sudo docker-compose up -d --build
sudo docker ps
sudo docker-compose logs --tail=100 backend
```

### 100. 최종 원칙

백엔드 배포 시 반드시 지킬 원칙은 다음과 같다.

```text
1. 브랜치를 파기 전에 develop pull을 먼저 받는다.
2. 변경사항이 있으면 git status로 확인하고 기록한다.
3. .env 실제 값은 팀원에게 확인한다.
4. CI/CD 실행 조건은 팀원에게 확인한다.
5. Dockerfile과 docker-compose.yml은 팀 기준에 맞춘다.
6. Grape.db 삭제 전 백업 여부를 확인한다.
7. 배포 후 docker ps와 logs로 정상 실행을 확인한다.
8. Restarting 상태면 로그부터 확인한다.
9. sqlite3 unable to open database file 오류는 DB 파일 마운트부터 확인한다.
10. 배포 결과와 특이사항은 팀에 공유한다.
```
