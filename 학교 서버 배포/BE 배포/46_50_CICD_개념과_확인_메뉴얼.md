# Toolnet.Be 배포 매뉴얼 46~50

## 46~50. CI/CD 개념과 확인 방법

### 46. CI/CD의 의미

CI/CD는 코드를 Git에 올렸을 때 자동으로 테스트, 빌드, 배포를 실행하는 흐름이다.

```text
CI: Continuous Integration
CD: Continuous Delivery 또는 Continuous Deployment
```

백엔드 프로젝트에서는 보통 다음 작업을 자동화한다.

```text
1. 코드 checkout
2. Python 설치
3. 의존성 설치
4. 테스트 실행
5. Docker 이미지 빌드
6. 서버 배포
7. 컨테이너 재시작
```

### 47. CI/CD 파일 위치 확인

GitHub Actions를 사용한다면 보통 아래 경로에 파일이 있다.

```bash
ls .github/workflows
```

예시:

```text
backend-deploy.yml
ci.yml
deploy.yml
```

GitLab CI를 사용한다면 보통 루트에 다음 파일이 있다.

```bash
ls -l .gitlab-ci.yml
```

Jenkins를 사용한다면 보통 다음 파일을 확인한다.

```bash
ls -l Jenkinsfile
```

### 48. 팀원에게 CI/CD 기준 물어보기

CI/CD 파일이 보이지 않거나 여러 개라면 팀원에게 확인한다.

질문 예시:

```text
백엔드 배포는 GitHub Actions로 하나요?
배포 workflow 파일 이름이 무엇인가요?
어느 브랜치에 push하면 배포가 실행되나요?
develop에 push하면 dev 서버 배포인가요?
main에 merge하면 운영 서버 배포인가요?
배포 실패 시 어디서 로그를 확인하면 되나요?
```

### 49. GitHub Actions 실행 위치

GitHub 저장소에서 CI/CD 실행 결과는 보통 다음 위치에서 확인한다.

```text
GitHub Repository
→ Actions 탭
→ 실행된 workflow 선택
→ 실패한 job 선택
→ 실패한 step 로그 확인
```

터미널에서는 GitHub CLI가 설치되어 있다면 다음처럼 볼 수 있다.

```bash
gh run list
gh run view
```

### 50. CI/CD 실패 시 먼저 확인할 것

CI/CD가 실패하면 다음을 순서대로 확인한다.

```text
1. 어떤 브랜치에서 실패했는가
2. 어떤 workflow가 실패했는가
3. 실패한 job 이름이 무엇인가
4. 실패한 step이 install, test, build, deploy 중 어디인가
5. 환경 변수 또는 secret 누락은 아닌가
6. Docker 빌드 실패인가
7. 서버 접속 실패인가
8. docker-compose 실행 실패인가
```
