# Toolnet.Be 배포 매뉴얼 26~30

## 26~30. 팀원에게 확인해야 할 배포 정보

### 26. 배포 전에 팀원에게 먼저 확인할 것

배포 작업을 시작하기 전에 혼자 추측해서 진행하지 말고, 팀원에게 다음 정보를 확인해야 한다.

```text
1. 현재 사용하는 브랜치 전략
2. 백엔드 기준 배포 브랜치
3. CI/CD 실행 조건
4. 서버 접속 방법
5. .env 작성 기준
6. DB 파일 관리 방식
7. Redis, DB, 외부 API 주소
8. Docker 이미지 이름
9. docker-compose.yml 서비스 이름
10. 배포 후 확인해야 하는 API 주소
```

이 정보가 없으면 배포는 되더라도 실제 서버 환경과 맞지 않을 수 있다.

### 27. CI/CD 작성법은 어디서 확인하는지 물어보기

CI/CD는 프로젝트마다 다르게 구성된다.

팀원에게 다음 내용을 물어봐야 한다.

```text
1. GitHub Actions를 쓰는지
2. GitLab CI를 쓰는지
3. Jenkins를 쓰는지
4. 배포 서버에서 직접 docker-compose를 실행하는지
5. push만 하면 자동 배포되는지
6. PR merge 후 자동 배포되는지
7. 배포 브랜치가 main인지 develop인지 release인지
```

질문 예시:

```text
백엔드 CI/CD는 어디 파일 보고 작성하면 되나요?
.github/workflows 안에 있는 파일 기준인가요?
어느 브랜치에 push 또는 merge해야 배포가 실행되나요?
```

### 28. `.env` 작성법은 팀원에게 확인하기

`.env`는 서버 환경마다 달라진다.

직접 임의로 값을 만들면 안 되고, 팀원에게 정확한 값을 받아야 한다.

질문 예시:

```text
백엔드 서버에서 사용하는 .env 예시 파일이 있나요?
DB_NAME, REDIS_HOST, REDIS_PORT 값은 운영 서버 기준으로 어떻게 작성하나요?
외부 API KEY나 SECRET 값은 어디서 받아야 하나요?
```

주의할 점:

```text
.env는 보통 Git에 올리지 않는다.
SECRET, TOKEN, PASSWORD는 노출하면 안 된다.
.env.example 파일이 있으면 그 형식만 참고한다.
실제 값은 팀원이나 서버 관리자에게 받아야 한다.
```

### 29. Dockerfile 작성 기준 확인하기

Dockerfile은 앱 실행 방식에 맞게 작성해야 한다.

팀원에게 다음 내용을 확인한다.

```text
1. Python 버전
2. FastAPI 실행 명령어
3. uvicorn 실행 포트
4. requirements.txt 사용 여부
5. DB 파일을 이미지 안에 포함하는지 여부
6. 컨테이너 내부 작업 경로
```

질문 예시:

```text
백엔드 Dockerfile은 Python 몇 버전 기준으로 작성하면 되나요?
uvicorn main:app --host 0.0.0.0 --port 8000 으로 실행하면 되나요?
컨테이너 내부 경로는 /app 기준인가요?
```

### 30. Docker Compose 작성 기준 확인하기

Docker Compose는 여러 컨테이너를 같이 실행하기 위한 설정이다.

팀원에게 다음 내용을 확인한다.

```text
1. backend 서비스 이름
2. redis 서비스 이름
3. 컨테이너 이름
4. 포트 매핑
5. .env 파일 연결 방식
6. Grape.db 마운트 방식
7. restart 정책
8. depends_on 사용 여부
```

질문 예시:

```text
docker-compose.yml에서 backend 서비스 이름은 backend로 맞추면 되나요?
Grape.db는 ./Grape.db:/app/Grape.db로 파일 마운트하는 방식이 맞나요?
Redis는 compose 내부 redis 서비스를 바라보게 하면 되나요?
```
